# Issue tracker: Local Markdown (`dev-docs/tickets/`)

Issues for this repo live as markdown files under `dev-docs/tickets/`, **not** in
GitHub Issues. The GitHub repo has issues enabled but holds none — do not create
issues there, and do not treat an empty `gh issue list` as "no work tracked".

## Structure

```
dev-docs/tickets/
├── INDEX.md              ← GENERATED by `make tickets-index`; never edit by hand
├── README.md             ← conventions, frontmatter schema, workflow, philosophy
├── TEMPLATE-platform.md / TEMPLATE-shared.md
├── shared/ ios/ android/ ← active tickets only (todo / in-progress)
├── archive/
│   └── shared/ ios/ android/   ← closed tickets (done / wontfix)
└── plans/                ← implementation plans (<ticket-id>[-<platform>].md)
```

IDs are `shared-NNN`, `ios-NNN`, `android-NNN`, numbered sequentially per prefix
across active **and** archived tickets. Filename: `<id>-<slug>.md`.

## Conventions

- **Never guess a filename or folder.** The slug does not always match the topic
  (e.g. `shared-013-timer-focus-mode.md` holds the timer state machine), and the
  folder depends on the status. Always glob `dev-docs/tickets/**/<ticket-id>-*.md`
  and drop matches under `plans/` (shared plans are named `<ticket-id>-ios.md`).
- **Status lives only in the YAML frontmatter** at the top of the ticket file —
  there is no `**Status**:` line and no Plattform-Status table.
  - Platform ticket: `status: todo | in-progress | done | wontfix`
  - Shared ticket: `status: { ios: …, android: … }`, same values plus `n/a`
    (platform not affected). One platform may be `done` while the other is
    `wontfix` (superseded by a later ticket).
  - Other fields: `id`, `title`, `phase`, optional `priority`, optional
    `depends_on` (ticket IDs only). Full schema: `dev-docs/tickets/README.md`.
- **Closed** = platform ticket `done|wontfix`; shared ticket: every platform value
  in `done|wontfix|n/a` and at least one not `n/a`. Closed tickets live in
  `archive/<area>/`, active ones in `<area>/`. Move with `git mv` so
  `git log --follow` keeps the history.
- **INDEX.md is generated.** After creating a ticket or changing any status, run
  `make tickets-index` from the repo root. It validates every ticket (frontmatter,
  ID vs. filename, folder vs. status) and fails with file + problem, leaving
  INDEX.md untouched. `make tickets-check` validates without writing and fails if
  INDEX.md is stale.
- **WONTFIX**: `status: wontfix` plus a `## WONTFIX` section stating why.
- **Ticket body**: `## Was` (what) and `## Warum` (why) up front, then
  `## Akzeptanzkriterien` as checkboxes, then `## Manueller Test`. Acceptance
  criteria are the implementation roadmap — `/implement-ticket` walks them
  one at a time under TDD. Free-text dependencies go under `## Hinweise`.
- Documentation is written in German with ASCII transliteration (`ae`/`oe`/`ue`),
  matching the surrounding files.

## When a skill says "publish to the issue tracker"

Use the `/create-ticket` skill rather than writing a file by hand — it assigns the
next free number (active + archive), fills the frontmatter from the template,
validates the ticket against the product philosophy in `CLAUDE.md`, and
regenerates `INDEX.md`.

## When a skill says "fetch the relevant ticket"

1. Resolve the ID from the branch name (`feature/<ticket-id>[-<platform>]`), the
   commit message (`<type>(<scope>): #<ticket-id> …`), or ask the user.
2. Glob `dev-docs/tickets/**/<ticket-id>-*.md` (excluding `plans/`) and read the
   file. Status, phase and dependencies are in its frontmatter.

## Related conventions

- **Branches**: `feature/<ticket-id>` or `feature/<ticket-id>-<platform>`.
- **Commits**: `<type>(<scope>): #<ticket-id> <description>`, where type is one of
  `feat`, `fix`, `refactor`, `docs`, `test`, `chore` and scope is `ios`, `android`
  or `shared`.
- **CHANGELOG.md**: every user-visible change gets an entry in `[Unreleased]`
  ending with `(Ticket: <ticket-id>)`. This is the source for release notes, so a
  ticket is not finished without it.

## Ticket lifecycle skills

The repo has its own skills for the full loop; prefer them over ad-hoc edits:

`/create-ticket` → `/plan-ticket` → `/implement-ticket` → `/review-code` → `/close-ticket`
